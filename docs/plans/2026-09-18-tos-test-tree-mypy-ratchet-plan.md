# tos 테스트 트리 mypy 래칫 계획 (유예 10종 해소)

- 작성일: 2026-09-18
- 성격: 실행 계획 (비규범). 게이트 강화 순서와 PR 단위를 정한다.
- 선행: PR #742(테스트 트리 mypy 결선) · PR #743(Black 커버리지 + 순서 주장 정정)
- **측정 시점: main `104fce1a`** — §1~§6 의 모든 수치는 그 커밋에서 잰 것이다.
  main 이 움직이면 낡는다. 재실행 방법은 §1.2 에 있다.
- **§1.1 표는 이미 낡았다.** 1·2단계가 착지하면서 다른 코드의 수치도 함께 움직였다
  (예: `attr-defined` 133 → 착수 시점 실측 **108**, `arg-type` 833 → **773**).
  **최신 실측은 §7.5 에 있다.** 착수 전에 §1.2 로 다시 재고, §1.1 은 **당시 판단의
  근거였던 값**으로만 읽어라 — 지우지 않는 이유가 그것이다.

## 0. 왜 이 문서가 있는가

PR #737 에서 테스트 **헬퍼**의 타입 결함(한 이름을 두 타입으로 재대입 — 단언을
무력화할 수 있는 자리)이 **리뷰 3라운드와 CI 3회를 전부 통과**했다. 원인은
`tos-firewall` 의 mypy 가 `src` 만 보고 두 테스트 트리를 보지 않은 것이었다.

PR #742 가 그 구멍을 닫았다. 다만 기존 부채가 커서 통째로 넣을 수 없었고, 두 가지
방식을 검토하고 **버렸다**:

| 버린 방식 | 이유 |
|---|---|
| 파일 단위 예외 목록 | 이 저장소가 이미 당한 **「레지스트리 + 고정 안 된 위성」의 재생산**. 새 파일이 조용히 미커버로 합류한다 |
| 베이스라인 에러 카운트 래칫 | 리뷰 규약 §5 가 금지한 **fingerprint** |

채택한 것은 **에러 코드 단위 유예**다. 코드 목록은 유한하고, 파일이 늘어도 썩지
않으며(새 파일은 생긴 순간부터 켜진 모든 코드로 검사된다), **줄어들기만 한다.**

#742 가 9종을 켰다(`assignment` · `method-assign` · `dict-item` · `str-bytes-safe` ·
`type-var` · `call-arg` · `call-overload` · `list-item` · `var-annotated`).
**이 문서는 남은 10종을 어떤 순서로 켤 것인가를 정한다.**

### 1.2 재측정 방법

```bash
# 대상 코드 하나만 켜고 나머지 9종은 유예한 채 재는 스크립트.
all=(arg-type no-untyped-def attr-defined return-value no-any-return \
     unused-ignore union-attr operator index misc)
for tree in tos/tests tos/runtime/tests; do
  for target in $all; do
    flags=()
    for c in $all; do [[ "$c" == "$target" ]] || flags+=(--disable-error-code=$c); done
    mypy $tree --ignore-missing-imports --no-error-summary "${flags[@]}" \
      | grep -c "\[$target\]"
  done
done
```

**두 함정을 피해야 한다** — 둘 다 이 측정을 실제로 틀리게 만들었다:

1. **플래그를 변수에 담아 `$VAR` 로 넘기지 말 것.** zsh 는 따옴표 없는 변수를 단어
   분할하지 않아 플래그 10개가 **인자 하나**로 전달되고, mypy 는 `Invalid error
   code(s)` 로 즉시 죽는다. 위처럼 **배열**을 쓴다.
2. **`2>/dev/null` 로 stderr 를 가리지 말 것.** 위 죽음이 가려진 채 `grep -c` 가 0을
   돌려주면 **「비용 0」으로 읽힌다.** 실제로 그렇게 읽고 보고할 뻔했다.
3. 두 트리를 **한 명령으로 합치지 말 것** — `mypy tos/tests tos/runtime/tests` 는
   `Duplicate module named "tests"` 로 중단되어 사실상 아무것도 검사하지 않는다.

## 2. 핵심 발견 — 코드끼리 간섭하지 않는다 (`unused-ignore` 하나만 빼고)

각 코드의 한계비용이 **전체를 켠 수치와 전부 같았다.** 유일한 예외가
`unused-ignore` 로, 전체 기준 53 대 한계 **283** 이다.

이유는 `unused-ignore` 만이 **다른 코드가 켜져 있는지에 의존**하기 때문이다.
`# type: ignore[arg-type]` 은 `arg-type` 이 꺼져 있으면 「불필요」로 보인다. 지금
green 을 만들자고 지우면 **나중에 `arg-type` 을 켤 때 필요한 억제를 미리 없애는
것**이라, 래칫을 쉽게 만드는 게 아니라 어렵게 만든다.

두 가지 결론이 따라온다:

- **순서를 고민할 필요가 없다.** 어떤 코드를 먼저 켜도 다른 코드의 비용이 변하지
  않는다. 비용과 신호만 보고 고르면 된다.
- **`unused-ignore` 는 반드시 마지막이다.** 그것은 다른 코드들을 **재는 도구**이지
  앞장서는 코드가 아니다.

정정 이력: PR #742 는 「다음에 켤 코드는 `unused-ignore`(53건)」라고 적었다. 위
이유로 **틀렸고**, PR #743 이 정정했다.

세부는 **집합 차로만** 말한다(아래 두 수는 `comm` 으로 잰 것이다):

| 갈래 | 건수 | 뜻 |
|---|---|---|
| 전체를 켜도 unused | **53** | 유예와 무관하게 **죽은 억제**. 283의 완전 부분집합이다 |
| 유예 때문에만 unused | **230** | 유예 코드의 에러를 실제로 억제 중 — 지우면 안 된다 |

**이 53건은 지금 당장 치울 수 있고, 치워야 한다.** 유예 상태와 무관하게 아무것도
억제하지 않는 `# type: ignore` 이고, **바로 그것이 이 아크에서 두 번 우리를 문
부류**다(PR #737 의 헬퍼, 그리고 `test_adapter.py` 의 죽은 `ignore[attr-defined]`
10곳 — 실제 에러는 `assignment` 였다). §3 의 어느 단계와도 독립이므로 **1단계에
얹거나 별도 소형 PR로 처리한다.**

이 문단의 이전 판(「228건 직접 일치 + 2건 캐스케이드」)은 **저자가 재지 않고 다른
리뷰의 표본을 옮겨 적은 것**이라 재현되지 않았다. 억제 코드 텍스트를 파싱해 원인을
1:1로 귀속하는 분해는 혼합 코드(`# type: ignore[call-arg, arg-type]`)와 캐스케이드가
섞여 신뢰할 수 없다 — **집합 차만 쓴다.**

### 2.1 `unused-ignore` 가 말하지 않는 것 — 「덮이지 않은 나머지」

**저자가 1단계 PR 에서 틀린 주장을 했고 #747 재심이 반증했다.** 틀린 주장이 그럴듯해서
반복될 만하므로 반증까지 함께 남긴다.

**틀린 주장**: 「라벨이 실제 에러 코드와 다른 `# type: ignore` 는 `unused-ignore` 로
안 잡힌다.」 **거짓이다.** 라벨이 가리키는 코드의 에러가 그 줄에 없으면 그 ignore 는
아무것도 억제하지 않으므로 `unused-ignore` 로 **정확히 잡힌다**(`warn_unused_ignores
= true`, `pyproject.toml:321`).

**실제로 일어나는 것**은 다른 일이다 — **한 줄에 에러가 둘일 수 있다.** ignore 가
하나를 **정당하게** 덮고, 다른 하나가 덮이지 않은 채 남는다. 그때 mypy 는 덮이지 않은
쪽을 그대로 내고 note 를 붙인다:

```
tos/tests/sci/test_sci_truthy_sentinel.py:48: error: "object" has no attribute "name"  [attr-defined]
tos/tests/sci/test_sci_truthy_sentinel.py:48: note: Error code "attr-defined" not covered by "type: ignore[index]" comment
```

이 note 의 뜻은 **「라벨이 틀렸다」가 아니라 「이 줄에 네 ignore 가 덮지 못한 에러가
더 있다」**이다. 그 `[index]` 는 같은 줄의 진짜 `index` 에러를 덮고 있으므로
`unused-ignore` 에 안 잡히는 것이 **옳다.**

**판별에는 절차가 필요 없다.** 라벨이 팬텀이면(= 그 코드의 에러가 그 줄에 없으면)
평범한 FULL 실행에서 **그 줄에 `unused-ignore` 가 그냥 뜬다.** 아래 4건은 FULL 에서
`unused-ignore` 가 **안 뜨므로** 팬텀이 아니다 — 그것이 전부다.

굳이 한 건을 더 확인하고 싶으면, **note 가 지목한 쪽**(덮이지 않은 코드)을 끈다.
**라벨이 가리키는 코드를 끄면 안 된다** — 끄는 순간 그 ignore 는 무엇을 덮고 있었든
구조적으로 「unused」가 되어 **판별력이 0이다.** 저자가 이 문서에 그렇게 잘못 적었다가
#747 2차 재심에서 잡혔다.

대조군까지 갖춘 실측(`test_sci_truthy_sentinel.py`, 109줄에 팬텀 `ignore[index]` 를
심어 대조군으로 삼음. 48줄은 진짜 `index` 에러 위의 `ignore[index]`):

| 실행 | 48줄 (덮고 있음) | 109줄 (팬텀) | 판별력 |
|---|---|---|---|
| 아무것도 끄지 않음 | 조용 | `unused-ignore` | **있음** |
| 라벨 코드(`index`)를 끔 | `unused-ignore` | `unused-ignore` | **없음** |
| note 가 지목한 코드(`attr-defined`)를 끔 | 조용 | `unused-ignore` | **있음** |

아래 4건은 이 방법으로 **전부 「덮고 있음」**임을 확인했다. 1차 재심은 같은 결론을
다른 방법(ignore 를 지우고 두 에러가 동시에 뜨는지 보기)으로 독립 확인했다.

따라서 `not covered by` 는 죽은 억제 탐지기가 아니라 **다음 단계가 red 를 낼 자리의
예고**다. 두 탐지기는 **서로 다른 것**을 재므로 둘 다 돌린다:

```bash
mypy <tree> --ignore-missing-imports --no-error-summary | grep -c 'unused-ignore'   # 죽은 억제
mypy <tree> --ignore-missing-imports --no-error-summary | grep -c 'not covered by'  # 덮이지 않은 나머지
```

**1단계 착지 시점 「덮이지 않은 나머지」 4건 — 전부 2단계 코드다:**

| 위치 | ignore 가 덮는 코드 | 덮이지 않은 코드 |
|---|---|---|
| `tos/tests/sci/test_sci_truthy_sentinel.py:48` | `index` | `attr-defined` |
| `tos/tests/afg/test_afg_void_canaries.py:149` | `arg-type` | `return-value` |
| `tos/tests/afg/test_afg_truthy_sentinel.py:96` | `arg-type` | `return-value` |
| `tos/runtime/tests/engine/test_replay_stage.py:58` | `operator` | `no-any-return` |

덮이지 않은 쪽이 `attr-defined`/`return-value`/`no-any-return` — **2단계가 켜는 바로
그 셋**이다. 2단계에서 반드시 red 가 되므로 **별도 PR을 만들지 않고 2단계에서
처리한다.** 라벨 정리가 아니라 **실제 에러 수정**이다.

**#737 `test_adapter.py` 의 죽은 `ignore[attr-defined]` 10곳은 이 부류가 아니다** —
실제 에러가 `assignment` 였으니 **팬텀 라벨**이고, 위 표의 첫 줄대로 `unused-ignore`
가 켜져 있었다면 그냥 떴을 것이다. 안 잡힌 이유는 탐지기의 한계가 아니라 **꺼져
있었음**이고, 껐던 것이 두 겹이다: 그때는 **테스트 트리가 게이트에 아예 없었고**(§0),
지금은 트리는 들어왔지만 **`unused-ignore` 가 아직 유예 중**이다(§3.4 에서 켠다).
그때까지 팬텀 라벨은 CI 에서 계속 안 보인다 — **로컬 FULL 실행에서만 보인다.**

## 3. 계층과 순서

### 3.1 1단계 — 한 PR (113건 / 약 46파일)

`misc` + `index` + `operator` + `union-attr`.

묶는 근거: 비용이 작고 파일이 집중돼 있다. **`union-attr` 43건은 전수가**
`Item "None" of "X | None" has no attribute` — 100% None 안전성이다. `operator` 는
28건 중 **21건**이 `Unsupported operand types for + ("None" and "int")` 류이고
**7건은 `"object" not callable`** 로 성격이 다르다. `index` 는 사실상 두 파일
(`test_evidence_scrub.py` 15 · `test_file_custody.py` 6)이고, `misc` 는 19/20 이
제너레이터 반환형 애노테이션이라 기계적이다.

넷에 **§2 의 「전체를 켜도 unused」 53건**을 얹는 것을 권한다 — 유예와 독립이고,
치우면 죽은 억제가 사라진다.

넷을 한 PR로 묶는 것이 §5 의 「PR 하나에 코드 하나」와 어긋나 보이지만, 합쳐도
113건이고 넷 다 같은 성격(좁은 지역 수정)이라 리뷰가 형식이 되지 않는다. **묶어서
리뷰가 어려워지면 쪼갠다** — 판단은 리뷰어 몫으로 남긴다.

### 3.2 2단계 — 개별 PR (304건)

`no-any-return`(55) → `return-value`(116) → `attr-defined`(133) 순. 작은 것부터
간다.

`attr-defined` 133건 중 23건은 `"AST" has no attribute "lineno"` 로 mypy 의 `ast`
유니온 처리 한계에서 온다. **운영자 처분(§6 ③): 타입 좁히기로 정면 처리한다** —
`isinstance` 분기 또는 정확한 ast 노드 타입 명시. **예외 축을 만들지 않는다.**

### 3.3 3단계 — `arg-type` 833

**성격을 실측으로 규정한다**(833건 전수 패턴 매칭):

| 패턴 | 건수 | 무엇 |
|---|---|---|
| `**dict` kwargs 언패킹 | **443 (53%)** | 헐겁게 타입된 dict 를 펼쳐 넣는다. 그중 114건만 `_*_strategies.py`/`_fixtures.py`/`conftest.py` 이고 **나머지 329건은 테스트 파일 본문** |
| `None`/`Optional` 불일치 | 112 | `operator`/`union-attr` 와 같은 None 안전성 계열 |
| 커스텀 더블(`_Stub*`/`_Fake*`/`_Mutable*` …) | **77 (9%)** | 더블이 Protocol 을 만족하지 않음 |

**저자의 초기 규정(「테스트 더블이 Protocol 미충족 — PR #742 의 `SealLookup` 과 같은
뿌리」)은 틀렸다.** 그 진단은 **9% 에만 맞는다.** 저자가 고른 표본 4건이 전부 더블
사례였던 탓이고, fact-check 가 더 넓게 표본해 잡았다. 지배적인 것은 **kwargs 언패킹**
이며, 이는 더블 계약 문제가 아니라 **팩토리·전략 헬퍼와 호출부의 타이핑 문제**다.

**집중도가 높다** — `test_brokercap_routing.py` 한 파일이 443 중 **96건**(22%)이다.
분할 축은 도메인이 아니라 **패턴 + 상위 파일**이 될 가능성이 크다.

세 가지를 못박는다:

- **77건(더블)에 대해서만**: 더블이 계약을 지키게 고친다. **Protocol 을 넓히지
  않는다.** 느슨하게 만들어 green 을 얻으면 프로덕션 타입 안전성을 테스트 편의로
  팔아먹는 것이다.
- **443건(kwargs)에 대해서는 다른 처방이 필요하다.** 팩토리 반환형을 좁히는 것이
  근본이고, 호출부마다 캐스트를 박는 것은 인스턴스 처방이다 — **어느 쪽인지 별도
  계획에서 정한다.**
- **한 PR로 하지 않는다.** 833건 단일 diff 는 리뷰가 형식이 된다.

이 단계는 **착수 전 별도 계획을 쓴다** — 위 세 패턴의 처방이 서로 다르고, 분할 축도
실측으로 정해야 한다.

### 3.4 마지막 — `unused-ignore`

§2 의 이유로 맨 끝이다. 앞 단계가 진행될수록 이 수치는 **저절로 줄어든다** — 283
중 230건이 「유예 때문에만 unused」이므로, 그 유예가 걷힐 때마다 해당 ignore 는 다시
「사용 중」이 된다. 마지막에 재면 남은 것이 진짜 죽은 억제다.

단, §2 의 **53건은 기다릴 이유가 없다** — 유예와 무관하게 죽어 있으므로 1단계에서
치운다.

## 4. 하지 말 것을 권하는 것 — `no-untyped-def` 623

**`check_untyped_defs = true` 가 이미 `pyproject.toml:318` 에 켜져 있다.** 즉
**애노테이션 없는 함수의 본문도 이미 검사되고 있다.** 실측으로 확인했다 —
`--check-untyped-defs` 를 명시로 켜도 `arg-type` 이 324 로 **변하지 않는다**.

따라서 623개 함수에 애노테이션을 채워도 **탐지력이 거의 늘지 않는다.** 스타일이지
안전성이 아니다. 그리고 623건/183파일 diff 는 의미 있는 리뷰가 불가능해, 이 저장소가
싫어하는 **형식적 승인**을 부른다.

**다만 선언과 게이트가 어긋나 있다** — 같은 `pyproject.toml:316` 이
`disallow_untyped_defs = true` 를 선언한다. 의도는 애노테이션을 요구하는데 게이트는
유예하고 있다. **운영자 결정 사항으로 남긴다**(§6 ①). 선언을 지키기로 한다면
codemod 로 일괄 처리하되 **「리뷰 가치 없음」을 PR 에 명시**하는 것이 정직한
방식이다 — 읽지 않은 것을 읽은 척하지 않는다.

## 5. PR 당 실행 규약

§5 에 두 항을 더한다.

8. 게이트 목록에 **`python tools/tos_completion_status.py --check` 를 반드시 넣는다.**
   1단계에서 실행 레인에 준 목록에 이것이 빠져 있었고, 그래서 로컬 전건 green 뒤에
   CI 가 RED 였다.
9. diff 가 **테스트 파일의 줄 수를 바꾸면**(`git show --stat` 의 삽입≠삭제) 그 파일이
   앵커돼 있는지 먼저 본다:

   ```bash
   # 경로를 필드로 정확 일치시킨다 — grep 에 그대로 넣으면 파일명의 `.` 이
   # 정규식 임의 문자가 되고, `^` 를 빼면 더 긴 경로의 접미사에도 걸린다.
   f=tos/tests/spg/test_spg_replay_substrate.py   # 줄 수가 바뀐 파일
   grep -oE '[A-Za-z0-9_./-]+\.py:[0-9]+' \
     tos-spec/src/verification/EVIDENCE-SURFACE-MAP.csv \
     | sort -u | awk -F: -v f="$f" '$1 == f'
   ```

   밀렸으면 **각 앵커를 현재 파일에서 다시 유도**한다. **GREEN 은 앵커가 옳다는 뜻이
   아니다** — 아래를 읽어라. 일괄 오프셋 가산은 틀린다 —
   삽입 지점이 여러 곳이면 앵커마다 이동량이 다르다.

**CSV 를 파이썬으로 다시 쓸 때의 함정.** `csv.writer` 의 기본 `lineterminator` 는
`\r\n` 이라, 13줄만 바꾸려 해도 **파일 전체(헤더 1 + 데이터 2023 = 2024줄)가 CRLF 로
재기입**된다. 앵커 값은 맞는데
diff 가 전 파일로 부풀고 blob 이 바뀐다. 조치 뒤 `git diff --stat` 의 변경 줄 수가
의도한 수와 같은지 확인하라 — 1단계에서 실제로 발생했고 diff 를 보고 되돌렸다.

**GREEN 의 의미를 정확히 못박는다 — 「앵커가 옳다」가 아니다.**
`tools/tos_completion_status.py:556 _resolve_path_line_basis` 가 요구하는 것은
**그 줄에 `evidence_id` 리터럴이 있을 것** 하나뿐이다. 같은 행의 `surface_ref`(pytest
nodeid)와 그 줄의 대응은 **검사하지 않는다.** 실측: `test_spg_replay_substrate.py` 는
`SPG-EV-012` 표지 줄이 **13개**인데 CSV 앵커는 **11개**다 — 즉 **11개를 서로 뒤바꿔
놓아도 GREEN 이다.**

읽는 법은 이렇다:

| 검사기가 잡는 것 | 잡지 못하는 것 |
|---|---|
| 앵커가 표지 없는 줄로 밀림 (= 줄 수 변화의 전형) | 앵커가 **같은 파일의 다른 표지 줄**을 가리킴 |

1단계가 RED 로 걸린 것은 왼쪽 부류였다(+3 이 전부 표지 없는 줄로 떨어졌다). 하지만
**일괄 오프셋 가산으로 「고치면」 오른쪽 부류를 만들어 GREEN 으로 통과시킬 수 있다.**
그래서 앵커는 각각 다시 유도해야 하고, **GREEN 을 조치의 충분조건으로 쓰지 않는다.**
이 한계는 #746 재심(`review-746b`)이 검사기 코드를 읽고 지적한 것이다.

607(79%)이 세 부류로 닫히고**, 나머지 140 이 흩어진 채 남는다. 별도 계획이 필요한
이유는 「형상이 없어서」가 아니라 **부류마다 처방이 다르고, 그 뒤에도 18%가 남기
때문**이다.

**그리고 이 분할은 두 번 갈렸다.** 272 → (132 + 140) → (81 + 51 + 140). 매번 저자가
「이제 됐다」고 썼고 매번 재심이 더 갈랐다. **3단계 계획은 이 숫자를 종점으로 읽지
마라** — 분류기를 바꾸면 또 갈린다.

### 7.7 2단계가 가르친 것

**① 근본을 먼저 찾아라 — 대개 한두 곳이다.** ②는 116건 중 108건이 커널 3줄, ③은 36건
중 21건이 헬퍼 한 줄이었다. 파일별로 고쳤다면 리뷰가 형식이 됐을 것이다. **`got`/주체
타입으로 묶어 보는 것**이 근본을 드러냈다.

**② 죽은 가드의 판별 기준은 「오늘 안 걸리는가」가 아니다.** 세 번 마주쳤고 판정이
갈렸다:

| 건 | 판정 | 근거 |
|---|---|---|
| #758 `assert row is not None` 9개 | **제거** | `SELECT COUNT(*)` 는 항상 한 행 — **어떤 입력으로도** 발화 불가 |
| #760 `assert isinstance(x, X)` 7개 | **제거** | `X.issue(...)` 는 classmethod 바인딩이 `X` 를 보장 — `Self` 와 무관하게 참 |
| #762 `assert isinstance(result, Path)` 1개 | **유지** | 파라미터가 `object` 라 **타입 체계가 허용하는 입력으로 도달 가능** — 리뷰어가 실제로 발화시켰다 |

기준은 **「타입 체계가 허용하는 입력으로 도달 가능한가」**다. 「지금 호출부에서 안
걸린다」는 기준이 아니다.

**③ 문언은 코드보다 틀리기 쉽고, 게이트가 안 잡는다.** #763 은 docstring **하나**에 세
라운드를 썼고 **매 라운드가 「결론은 맞고 근거가 틀린」 것**을 잡았다(「불가능」 → 모호한
「도달 가능」 → 틀린 인과). 하필 **그 부류를 고치려고 연 PR** 에서 두 번 반복했다.
mypy·pytest·ruff 중 무엇도 문언을 검사하지 않는다 — **리뷰만 잡는다.**

**④ 게이트를 켜면 건드리지 않은 코드에서도 red 가 날 수 있다.** ②의 커널 `Self` 수정이
**이미 켜진** `operator` 에서 3건을 새로 드러냈다. §2 의 「코드끼리 간섭하지 않는다」는
**유예 설정**에 관한 주장이지 **소스 변경**에 관한 것이 아니다. 근본 수정 뒤에는 유예
목록에 없는 코드도 다시 돌려라.

**⑤ editable 설치가 측정을 조용히 무효로 만든다.** `.pth` 가 **메인 워크트리를 하드코딩**
으로 가리키므로, 워크트리에서 커널을 고치고 테스트 트리를 재면 **수정 안 된 커널**로
잰다. 저자가 실제로 걸려 「116 그대로」라는 허수를 얻었다. **커널을 고치는 PR 은
`PYTHONPATH`/`MYPYPATH` 를 걸고, 측정 전마다 `python -c "import tos; print(tos.__file__)"`
로 확인해라.** `pip install -e` 재설치는 해법이 아니라 원인이다(다른 레인의 설치를
덮어쓴다).

**⑥ 캐시가 뮤테이션 검증을 조용히 무효로 만든다 — pytest 와 mypy **둘 다**.** 같은
byte 길이의 단일 문자 교체를 같은 tick 안에 두 번 하거나 mtime 을 복원하면
`(mtime, size)` 가 안 바뀐다. 그러면:

- **pytest** 의 assertion-rewrite 캐시(`__pycache__`)가 **뮤테이션 시점 바이트코드를
  계속 낸다.** 원복했는데 실패가 계속 보이거나, 더 나쁘게는 뮤테이션했는데 통과가
  보인다.
- **`.mypy_cache` 도 같다.** mypy 는 `(mtime, size)` 가 일치하면 내용 해시를 다시
  계산하지 않고 캐시를 믿는다. `mypy --help` 에 `--skip-cache-mtime-checks` 가 있는
  것 자체가 **기본 동작이 mtime 기반**임을 말한다.

**저자는 여기서 「mypy 는 면역」이라고 적었다가 #764 재심에 반증당했다.** 저자의 원
실험이 결함이었다 — `cp` 를 `-p` 없이 써서 백업본의 mtime 이 **복사 시각**으로 찍혔고,
그것을 `touch -r` 로 되돌리는 바람에 **mtime 이 실제로는 바뀌어 있었다.** `cp -p` 로
다시 하면 mypy 는 `Int` 같은 미정의 이름을 심어도 **green 을 낸다**(실증).

그 잘못된 문언이 PR #760 본문과 실행 레인·리뷰 레인 지시 네 곳에 이미 번졌다. **틀린
지침은 옳은 지침보다 멀리 간다** — 「안 해도 된다」는 쪽이 편하기 때문이다.

**그러므로 뮤테이션 검증 전후로 둘 다 지운다:**

```bash
find <트리> -name __pycache__ -exec rm -rf {} +
rm -rf .mypy_cache
```

**3단계(`arg-type` 773)가 이 방법론 위에 선다.** 이 문언이 틀린 채로 남았다면 3단계의
「게이트가 실제로 red 를 내는가」 증명이 **거짓 green** 을 낼 수 있었다.
