# 작업 메모 — TOS 엔진 층(Part 2/3) 완주 경로 평가 (2026-07-29)

> **문서 성격 (규범성 선언)**: 본 문서는 **비규범 작업 메모**다. **비준(ratification) 대상이 아니며**,
> GOV-001의 세 거버넌스 행위(비준 / ADR acceptance / live authorization) 중 어느 것도 수행하지 않는다.
> ADR·RFC·VER·register의 어떤 상태도 변경하지 않고, 어떤 EV 항목도 이동시키지 않는다. 본 문서의
> 유일한 산출은 **ADR-002 시리즈 완주 이후 엔진 층(Part 2 RFC-003~007, Part 3 RFC-008~011) 개발
> 방향에 대한 운영자-검증 평가 기록**이다. 여기 기록된 권고는 후속 설계 사이클의 입력물일 뿐,
> 설계 비준·구현 승인이 아니다.

- **발단**: 운영자 질문(2026-07-29 브레인스토밍 세션) — "RFC 주도 Trading Operating Platform이
  정말 정교하게 만들어지고 BackTrader/NautilusTrader와 유사한 성과를 낼 수 있는가?"
- **운영자 확정 전제**: ① 성과의 축 = **종합(완주 가능성)**, ② 완주의 정의 = **완전 대체**
  (TOS가 결정/시장/실행/리스크 모델 + DSL까지 전부 구현해 기존 `shared/` + `services/` 런타임을
  은퇴시키고, 실계좌 라이브까지 TOS 위에서 도는 것).
- **검증 방식**: 섹션별 제시 → 운영자 확인 (총평 / 난이도 구조 / 경로 권고 / 외부 참조 전략 4개
  섹션 전부 승인됨).

## 1. 총평 — 3축 판정

"유사한 성과"는 단일 답이 없다. 축을 나누면 답이 서로 다르다.

| 축 | 판정 |
|---|---|
| **안전·거버넌스** | **이미 두 프레임워크를 넘어섰다.** BackTrader/NautilusTrader 어느 쪽에도 안전 케이스, 증거 캡슐, fail-closed 술어 계층, kill-switch 거버넌스, LLM 저작 전략의 독립 리뷰 체계가 존재하지 않는다. 이 축은 비교 대상 부재 — 두 프레임워크가 애초에 이 문제를 풀려 하지 않았다. Part 1 구현(28+ 패키지, 5,600+ 테스트, 뮤테이션 검증)이 실증. |
| **엔진 기능·성능** | **NautilusTrader 파리티는 비현실적이고 불필요하다.** NT의 Rust 코어·나노초 이벤트 루프·수십 개 거래소 어댑터는 수년간의 전업 팀 산출물. 우리의 실제 요구 봉투는 KIS 단일 브로커·한국 주식/선물·분봉 중심이며, 이 봉투에서는 **BackTrader급 이벤트 기반 백테스트 + 현실적 체결 모델**이면 충분하고 도달 가능하다. |
| **완주 가능성** | **가능하나, 최대 리스크가 여기 있다.** 남은 엔진 층 작업량은 지금까지 완료한 Part 1보다 크다고 추정된다. 모든 ADR이 아직 `Proposed`이며, 실행된 증거(EV-L2+) 없이는 어떤 것도 수락되지 않는 구조를 스스로 정의해 두었다. 다음 단계 설계를 잘못 잡으면(§3의 수평 전개 관성) 엔진 층에서 좌초할 실제 확률이 있다. |

**도달점의 정직한 정의**: "NT급 범용 엔진"이 아니라 **"안전축에서 NT를 넘어서는 KIS 특화
자율 트레이딩 OS"**.

## 2. 엔진 층이 질적으로 다른 난이도인 이유

Part 1의 성공 방식이 엔진 층에 그대로 이식된다고 가정하면 안 된다.

**Part 1 = 닫힌 세계.** 순수 술어, I/O 없음, 시간조차 `tos.time`이 데이터로 모델링. 이 세계에서는
"문서 우선 설계 → property 테스트 → 뮤테이션 검증" 파이프라인이 정확성을 **증명**할 수 있었다.

**엔진 = 열린 세계.** 정확성의 성격 자체가 바뀐다:

1. **경험적 정확성**: 백테스트 충실도(체결 모델·슬리피지·비용 — ADR-DEV-010)는 증명이 아니라
   **보정(calibration)** 의 문제. 실제 KIS 체결 데이터와의 대조로만 검증되며, property 테스트가
   원리적으로 닿을 수 없다. EV-L2+ 실행 증거 요구가 정확히 이 지점이다.
2. **통합 실패 모드**: 실전 시스템에서 fail-open 버그가 실제로 사는 곳은 술어 내부가 아니라
   **배선(wiring)** — 이벤트 루프가 술어에 올바른 입력을 올바른 시점에 공급하는가. 28개 패키지의
   seam은 아직 한 번도 실제 이벤트 흐름을 받아본 적이 없다.
3. **비동기·장애**: WebSocket 단절, 토큰 만료, 부분 체결, 크래시 후 상태 재조정. 현 파이프라인은
   이 규율로 async 코드를 생산해 본 적이 없다.
4. **재도출 비용**: 기존 `shared/`에 축적된 KIS 경험 지식(rate limiter, pseudo-OCO, 장 운영시간,
   토큰 수명)은 greenfield + import-firewall 판정(전략 B, 설계 #1) 때문에 직접 재사용 불가.
   **완전 대체의 최대 일정 승수.** (합법적 이전 경로는 §3-3.)

## 3. 완주 경로 권고 (운영자 승인, 5개)

**핵심: ADR-002 완주 후, Part 2를 수평 전개하지 말고 수직 슬라이스부터 뚫는다.**

1. **수직 슬라이스 우선.** RFC-003~007을 또 하나의 30-ADR 수평 시리즈로 분해하는 관성은 좌초
   경로다. 최소 경로 — DSL로 표현한 단순 전략 1개 → 이벤트 기반 백테스트 → paper 주문 1건 — 을
   끝까지 뚫는 것이 먼저다. 이유: (a) 28개 술어 패키지 seam이 실제 이벤트 흐름을 받는 첫 실증,
   (b) EV-L2 실행 증거의 조기 확보, (c) 배선 층 fail-open 발견은 빠를수록 싸다. 슬라이스에 필요한
   ADR만 선별 분해한다(RFC-005 실행 모델 + RFC-008 DSL 코어 + RFC-004 시장 모델 일부).
2. **NT에서 훔칠 것은 Rust가 아니라 구조.** 백테스트와 라이브가 **단일 이벤트 기반 코어**를
   공유하는 설계 — 백테스트↔실전 괴리를 구조적으로 줄이는 NT의 진짜 자산이며, 순수 Python으로도
   분봉 규모에선 충분히 구현 가능하다.
3. **기존 지식의 합법적 이전.** 방화벽은 import를 막지, 지식을 막지 않는다. (a) KIS 경험 상수
   (rate limit, 토큰 수명, 장 운영)는 **비규범 Broker Capability Profile 인스턴스**로 추출해
   `tos.brokercap`이 소비(tos-spec 브로커 불가지 원칙 유지 — KIS 사실은 규범 문서에 넣지 않는다).
   (b) `shared/backtest`를 **차등 테스트 오라클**로 사용 — 같은 데이터에 두 엔진을 돌려 결과 대조.
   import 없이 검증 자산만 이전된다.
4. **파이프라인 변형.** 엔진 층에는 property 테스트에 더해: 결정론적 리플레이 시뮬레이션, 장애
   주입(단절/부분체결/크래시 복구), 보정 게이트(paper 체결 vs 백테스트 체결 괴리 예산 —
   WDR[ADR-002-026]의 deviation budget 개념 재사용).
5. **YAGNI 경계 고정.** 멀티 거래소 어댑터, 나노초 클록, 범용 자산 클래스는 만들지 않는다.
   KIS 단일, KRX 시간, 분봉 + 필요 시 틱.

## 4. 외부 참조 전략 — pykis·한국투자증권 공식 GitHub

운영자 질문: "pykis, KIS 공식 GitHub 코드 등을 참조해 개발하면 리스크가 줄어드는가?"
판정: **예, 그러나 줄어드는 것은 어댑터 정확성 리스크(엔진 작업의 대략 15~20%)뿐이다.**

### 4.1 줄어드는 것 — 어댑터 정확성 리스크

- **`koreainvestment/open-trading-api`(공식 GitHub)** = TR ID, 요청/응답 필드, hashkey,
  WebSocket approval_key 등 **API 의미론의 권위 원전**. Broker Capability Profile 인스턴스
  저작 시 규범 참조로 사용하면, 역공학 대신 원전 대조가 되어 현 파이프라인의 인용-실측 규율이
  그대로 작동한다.
- **pykis(Soju06)·mojito(sharebook-kr) 등 커뮤니티 라이브러리** = 공식 문서에 없는 실전 quirk
  (토큰 발급 분당 제한, 세션 수 제한, 모의/실전 도메인 차이, 재연결 패턴)의 선행 사례집.
- 단, **가장 풍부한 오라클은 이미 내부에 있다** — `shared/kis`는 수개월 모의투자 운영으로 검증된
  경험 지식이며, 외부 참조는 이를 교차 검증하는 2차 원천이다.

### 4.2 줄어들지 않는 것 — 지배적 리스크 3개 (§2 불변)

1. 백테스트 충실도/보정 — pykis에도 공식 코드에도 백테스트 엔진이 없다.
2. 술어 28패키지 ↔ 이벤트 루프 배선(seam) 통합 — 외부 코드가 건드릴 수 없는 고유 구조.
3. 단일 이벤트 코어(백테스트/라이브 패리티) 아키텍처 — 참조 대상 자체가 NT이지 KIS 생태계가 아니다.

### 4.3 경계 — "참조"와 "의존"은 다르다

- pykis를 **의존성으로 채택**하는 것은 별개 사안이다. egress 경로에 커뮤니티 라이브러리를 싣는
  것은 정확히 **SCI(ADR-002-029, 공급망 무결성)** 술어가 게이트하도록 설계된 사안 — 출처 증명·핀
  고정·독립 admission 요구가 붙는다.
- **권고**: 외부 코드는 **문서로 취급**(참조·프로파일 저작·quirk 대조)하고, 어댑터 코드 자체는
  greenfield 저작 유지. 코드 차용이 필요해지면 라이선스 확인 선행(공식 repo 포함) + SCI 게이트 통과.

## 5. 후속 트리거

- ADR-002 시리즈 완주(#28 SIR·#29 SCI·#30 STM) 후, 본 메모 §3-1의 **수직 슬라이스 설계 문서**
  저작이 다음 사이클이다. 그 설계는 본 메모를 입력물로 인용하되, 규범 판정(EV 매핑·소유권·seam)은
  해당 설계 문서가 스스로 수행해야 한다.
- 본 메모의 어떤 문장도 grep 없이 인용하지 말 것(시리즈 규율: phantom 금지).
